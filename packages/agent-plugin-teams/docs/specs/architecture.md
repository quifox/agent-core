# Teams 插件规范

## 对象与职责

- 多个普通 Agent 显式共享同一个 TeamsPlugin 对象。每个成员持有独立的会话组合；模型、提示词、工具及其他插件由调用方分别选择。
- 任意成员都可由调用方直接 run/stream，也可由 Teams 唤醒。Teams 不定义固定 Leader、Top 接收者或替代 Agent 入口。
- 成员名称、Agent 引用及对应 Conversation 在首次运行前显式登记。成员身份使用 ctx.plugins 中的 Conversation 对象引用识别，不从插件 id 推导，不把成员身份加入 Core Context。
- 同一团队内成员名称、Agent 与 Conversation 一一对应；运行期间不改变成员集合。不同团队使用不同 Teams 对象。
- Teams 只拥有成员信箱、消息投递、接收等待和唤醒状态。消息历史、模型请求、存储、协议和 Fork 仍属于各成员的原插件。

## 团队生命周期与原入口返回

团队对象随宿主持有而长期存在，没有内置 completed、stopped 或“全队任务结束”状态。所有成员 idle 不销毁团队；后来投递消息或直接调用任意原 Agent 都能再次启动工作。

调用 A.run 只返回 A 本次调用的 Outcome，不等待 B/C/D 完成，也不会因为 A 后来被自动唤醒而让已完成的 Promise 返回第二次。自动唤醒是一次新的普通 Agent.run，其过程与结果可由成员 Events 出口另行观察。

某个成员的 run 返回值不会自动成为发给上次发送者的团队消息。通信必须显式调用 team_send 或宿主 send；模型没有发信时，Teams 不补造汇报。业务角色、任务结束、核验条件和汇总展示均由具体提示词、宿主或另一个插件定义；本插件不根据角色名称、回复正则或“最终报告”文本判定完成。

## 消息与工具

- onInitialize 在各成员的原 ToolRegistry 注册 team_send 和 team_receive。执行仍经过 Core 的唯一工具入口，调用参数不携带 Context。
- team_send 指定一个或多个收件人及内容；发送者由执行 Context 识别。全部收件人有效后才投递，重复收件人只投递一次。发送立即返回投递回执，不等待对方任务完成。
- 每条消息有团队内部顺序身份、发送者、收件人及内容；此身份不是 Core runId。信箱按投递顺序排列。
- team_receive 只接收当前成员的未读消息。已有消息立即返回全部待收消息，并从信箱取走；没有消息时等待新投递。
- timeoutMs 默认 10000，支持零等待；超时返回空消息及 timedOut=true，不取消其他成员、不伪造任务完成。投递到等待中的成员时立即结束等待并清理计时器。
- 同一消息只交给一次接收操作。信箱与等待均为进程内状态，不承诺宕机恢复或持久化消息总线。

## 中心邮箱通知

通知沿用共享可变对象语义，不隐式冻结或复制信件；需要独立快照的订阅端自行复制，网络出口应立即编码。订阅本身不领取业务消息。

- Teams 提供消息事件订阅，投递完成时发布 message-posted，领取时发布 message-received；普通工具和外部直接 send/receive 都经过同一事实位置。
- 订阅返回取消订阅函数。观察者失败不回滚投递、不改变唤醒，也不产生未处理的 Promise rejection；失败可由调用方查询。
- 事件使用原团队消息身份关联投递与领取。UI 只维护展示记录，不通过 receive 刷新，不占用成员的未读消息。
- 消息通知与各 Agent 的执行事件来源独立；不要求四个事件插件各建一份中心邮箱。
- 发送时间和 UI 领取标签属于订阅 Host 的展示记录；TeamMessage 不添加 Core runId 或展示专用的传输字段。

## 自然结束与唤醒

- 空闲成员收到新消息后，由 Teams 在后续事件回合调用原 Agent.run，输入使用固定的新消息提示词；已有会话由该成员的 Session 继续维护。
- 正在运行或收尾的成员只接纳消息，不启动第二次执行。外部直接 run/stream 通过现有初始化、onRunStart、onRunEnd 钩子参与同一调度状态。
- 前置运行接纳插件可能在 Teams 之前合并调用；没有进入 Teams.onRunStart 的 Outcome 在 onRunEnd 中直接忽略，不改变成员状态或安排唤醒。
- 首次初始化已经完成、但消费者在 Teams.onRunStart 前关闭 stream 时，Teams 必须释放仅用于初始化窗口的 running 标记；该调用没有成为成员运行，也不能永久阻塞后续投递。
- Teams 不改变模型结果，不要求模型接收消息后才能结束。自然结束后，待收新消息可触发下一次运行。
- 同一批消息最多触发一次已进入运行阶段的自动唤醒；成员持续不读取该批消息不会形成无限自动运行。后续新消息可再次唤醒。
- 每名成员最多一个待执行唤醒检查和一个由 Teams 发起的运行；投递与收尾合并同一检查。
- 对外成员状态只有 running 与 idle。初始化、执行及尚未完成交接的收尾阶段统一属于 running；内部 Outcome 交接标记不是第三种业务状态。
- Teams 必须位于最后一个拥有异步收尾状态的插件位置。显式声明 `after: 'teams'` 的同步协调尾对象可以位于其后，例如 Steering 的完整收尾交接；这类尾对象不得等待存储或外部 I/O。Teams 只安排下一事件回合的检查，不 await 自己的下一次 run；Core 不维护 active。
- 延后检查重新读取当前成员状态与信箱。旧 Outcome 的收尾不得把已开始的新运行标为空闲；外部新运行优先保留原入口语义，不由 Teams 包装或排队。
- 初始化至 onRunStart 的入口窗口由 Teams 自己的初始化标记及会话接纳策略保护。未进入 Teams 运行阶段的唤醒失败保留信箱，不通过轮询或异常重试强行进入；可由当前外部运行的收尾或后续新投递重新安排。
- 成功 Outcome、无显式停止产物且无收尾错误时可在收尾后自动唤醒。失败、主动停止、长度/过滤终态及消费者提前关闭不立即重启同一批消息；后续新投递或调用方再次 run 可继续处理。
- 后台运行显式检查 Outcome.ok；成功与失败均由插件接纳，不产生未处理的 Promise rejection；失败保留尚未领取的消息并提供成员状态供调用方检查，不隐式重试模型或工具。
- 后台唤醒只有真正进入 Teams.onRunStart 后才算覆盖当前消息版本。若前置插件提前 stop 或拒绝，使唤醒没有进入 Teams，本插件不得针对同一批未读消息立即重复调度；新投递或调用方后续显式运行可以再次触发检查。

## 提示词与组合边界

- Teams 为每个成员贡献名称、成员名单和发送/接收工具用法，不替换调用方的专家提示词。
- 专家身份复用已有 createSystemPromptPlugin；不同成员可以组合不同提示词和不同工具插件。
- Teams 在该成员 onInitialize 一次贡献成员名单和通信 system 内容；其他系统提示词插件在 beforeModel 按会话内容去重。重复 Hook 调用不等于每次 run 重复插入相同 system 消息。
- 自动唤醒要求先通过 team_receive 读取消息，再根据原有职责处理或向其他成员发信。各次 run 的返回仍是原 AgentRunOutcome，不代表整个团队所有后台工作已经完成。
- Teams 通过普通工具、公开钩子与 Conversation 能力实现通信、成员发现和唤醒；Core 的入口、循环与统一收尾遵守原合同。

## 必须验证的边界

- 四个成员共享 Teams、独立会话；任意成员可从原 run/stream 入口发起任务，提示词及工具差异保留。
- 发送唤醒空闲成员，正在运行时仅入信箱；双向通信的发送工具不等待对方完成。
- 接收默认十秒超时、零等待、提前送达和多个等待者之间的单次交付；结束后无残留计时器。
- 真实异步 Session 收尾完成后再唤醒；收尾间隙新消息不丢失，外部新运行不被旧收尾覆盖。
- 首次 run-start 后立即关闭不会残留 running；前置插件提前结束自动唤醒不会形成零延迟循环。
- 忽略同一批消息不会无限唤醒，新消息仍可触发下一次运行；后台失败与主动停止不形成自动重试。
- 错误收件人不部分投递；错误成员绑定和收尾顺序在模型发送前明确失败。

- 长期 CTX 仅用于发现成员，运行令牌使用本次 Outcome 对象。重复 Teams 位置在同一 Outcome 下幂等接纳并累计收尾位置，不把旧调用释放为新调用的空闲状态。

行为验收见 [Teams 真实 Core 组合测试](../../test/plugin.test.ts)：A 分派后返回、B 延迟回信后重新唤醒 A、任意成员原入口与 Steering、未读消息防空转和异步收尾交接。
