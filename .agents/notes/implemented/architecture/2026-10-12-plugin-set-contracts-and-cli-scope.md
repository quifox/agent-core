# 插件集协作与 CLI 范围决定

状态：implemented，表示设计决定已采用，不表示下列功能已经实现或验收。当前行为仍以源码、模块 SPEC 与运行证据为准。

## 自由度与协作约定

Core 提供开放的插件、Hook 与 CTX；每套插件集自行确定协作契约。允许开发者选择不同契约或不参与某套约定，但偏离约定后不能假定该插件集仍能协调工作。自由度不等于开发时不需要契约，也不要求 Core 对所有第三方插件强制一套能力接口。

长期约束的权威正文见 [跨包架构 SPEC](../../../../docs/specs/architecture.md#实验性与契约取舍)，不在本 Note 复制接口字段。

## 插件重设计范围

- 以当前需求和 Core 最小执行合同重新设计，不以旧插件实现为新方案的约束。已有 Memory 能力保留组合接入，不能仅因独立主 checkout 尚未包含它就当成未实现。
- 首批实现一个 Chat 协议 Model 模组；所选插件集约定生成结果、流式事件、模型元数据与错误语义。其他供应商可独立提供 Model 插件，但不把多供应商实现作为当前验收条件。调用方不组装独立 Provider 插件。
- 工具与能力保持独立职责，优先显式组合；组合层注入合作需要的小接口，不在能力插件内直接依赖另一个插件实现。
- 安全重试区分未执行、已完成与结果未知；写操作的安全重放依赖真实幂等保证或结果核实，不从错误或取消推断副作用未发生。
- 打断请求与续跑中的工具处理策略分开。续跑有两种模式：继续原工具轮，对未执行调用继续、对未知调用先核实或安全重试；或补齐明确的中断/未知回执，交给模型重新规划。
- 消息插入支持消息引导与消息排队两种模式；参考成熟 CLI Agent 的行为，由开发者确定接纳、停止和顺序规则并用测试验证，不要求用户逐项指定实现。
- 上下文压缩支持配置文件：有效 context 取模型原始容量与用户配置的最小值，触发阈值取 `有效 context - maxOutputTokens - 安全余量` 与可选 `compactTokens` 的最小值；阈值无效时明确报错。模型资料支持 models.dev 与用户配置，目录元数据不证明账户或端点可用。
- Subagents 纳入首批，行为参考 Codex：启动、发送后续消息、等待、读取结果与停止。标准 Agent Skills 与 AGENTS.md 发现、作用域及按需读取由独立插件提供。
- 普通 Promise 工具由现有 Core 等待；后台工具由插件持有任务与结果，提供查询、等待和取消。新增能力不修改 Core 源码。

## CLI 与持久化

项目与宿主品牌统一为 QuiFox，TUI 使用狐狸标识与 QUIFOX。先实现 CLI，再实现 Desktop；两者共享 Agent、会话、工具、权限、恢复和插件组合，只替换交互适配与宿主连接。CLI 的文件、终端和进程能力留在对应适配器，不把本地能力变成所有运行时的前提。

狐狸采用蓝身体与黄耳朵；Host 默认用户目录采用 `.quifox`，保存配置、会话与插件资料。跨会话发送消息优先级低，主能力完成后再考虑。

CLI 会话与执行恢复数据使用本地 JSONL 持久化。会话恢复需要保存真实消息、调用与回执；不因该需求引入服务端数据库或分布式持久化系统。

权限与人工确认由 CLI/TUI 提供交互，工具携带自身 policy，策略插件据此对 read 等不同工具类型选择处理方式。Model 返回与事件合同、工具恢复和消息接纳等技术细节由开发者依据成熟方案设计、验证；只有改变产品范围或用户行为的重要取舍才需要用户决定。

### 2026-10-13：完全访问与展示权限

- 用户明确：完全访问模式下任意操作不再增加应用侧权限限制或逐次审批；不能另加目录白名单等不必要约束。
- open_view 是读取和展示操作，应支持任意目录中的文件。会话工作目录仅作为相对路径的解析基准，不是它的访问边界；GUI 用户选目录与浏览文件不要求先创建会话。
- 不为展示插件另建权限配置。Tauri 媒体协议需要的资源映射只是加载已选择内容的实现机制，不能演变为第二套业务权限或项目目录限制。
- 独立审查意见须由主实现者对照需求、行为与证据核验；不因审查者建议就扩展限制。拒绝“无会话只能读取已配置或已打开目录”及“open_view 只能读取所属会话工作目录”的建议，原因是它们把其他工具集的目录边界误用于只读展示。

MCP 以标准工具 list/call 接入为范围，使用标准客户端与相应传输，不借此引入另一套任务调度或恢复系统。

## 范围与优先级

- 当前不支持沙箱，不因 Code Mode 或 CLI 自动扩展为沙箱项目。
- 不默认添加模型 step、运行总时长或任务总 Token 限制；面向长任务，不能把预算控制当作成熟框架必备功能。容量与具体 I/O 边界见架构 SPEC。
- Desktop 的调用轨迹展示以 DSH 为行为参考；独立评测不在本轮范围。
- Teams 保留已有实现；团队配置、启动与跨团队协调优先级低，不纳入本轮两阶段必需验收。
- Plan 阶段 Fork 同一上下文前缀、保持子 Agent 空闲、实现后再唤醒审查，作为更低优先级的使用方式记录。优先复用 Subagents 的被动分叉与后续消息能力，不先创建独立审查插件或 Skill；Fork 保留的是该时刻真实可用上下文，不宣称自动恢复已压缩前的全部原文。
- 插件资源生命周期的扩展机制可后续单独解决。当前实际打开的连接、订阅与进程仍需明确关闭责任，不以完整生命周期框架阻塞功能开发。

## TUI 与 Bun 选型

CLI 使用 React + Ink。组件测试使用 Ink 的测试设施，真实终端交互另外使用 PTY 验证：输入、流式输出、批准/拒绝、停止、续跑、尺寸变化与退出。组件帧或字符串快照不能代替真实终端验收。

Desktop 采用 Tauri 2 + React + Bun sidecar；Rust 负责窗口与进程桥，Agent 能力继续由共享 TS/Bun 引擎和插件提供。UI 行为参考 Codex Desktop。Codex 与 DSH 作为行为锚点，不作为本项目内部架构或实现语言的模板。

采用 Bun 管理 workspace、依赖与脚本，并作为 CLI Host 的运行时。保留 TypeScript 编译和现有 Vitest 测试，避免在工具链迁移时改变测试语义；运行边界由 [包 SPEC](../../../../docs/specs/packages.md#构建边界) 维护。Core 与通用插件保持跨运行时的 TypeScript/ESM 边界，Bun 专用 I/O 留在 Host。React + Ink 的 TUI 与相关测试仍需实际实现和验收。

初期可以用 Mock LLM 验证生成合同、组合、打断、续跑与消息时序；合成输出不替代真实供应商链路的验证证据。
