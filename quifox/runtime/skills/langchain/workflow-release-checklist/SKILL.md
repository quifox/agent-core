# 工作流发布前风险覆盖清单

这是**提醒和参考**，不是强制验收流程。不同工作流的复杂度、部署方式和风险差别很大，不需要逐条运行故障注入，更不需要为不存在的能力建立测试基础设施。用户未要求测试时，不主动创建测试脚本、停止进程或实施故障模拟。

## 怎样使用这份清单

1. **识别应用边界。** 先了解任务是否只读、是否有外部写操作、是否需要跨进程恢复、是否并行、是否对外提供 API、是否多租户。
2. **筛掉不相关项。** 没有并行执行，就不必测并行恢复；没有外部写操作，就不必测写入后的重复副作用；不部署 API，就不必测 API 重连。
3. **选择成本最低的可靠证据。**
   - **看代码即可**：能力根本不存在、分支不可达、已有显式权限或简单确定性逻辑可判断时，直接给出判断。
   - **参考已有测试**：优先复用现有单元、集成或端到端测试，不为了凑清单重新编写测试。
   - **轻量模拟**：Mock / Stub 即可确认工具异常处理时，可选择一个代表性用例。
   - **隔离故障演练**：仅在真正依赖跨进程恢复、幂等或调度可靠性，并且有隔离环境和相应授权时，考虑进程终止、存储故障等实验。
4. **提醒而不是拦截。** 只描述发现的风险、已有证据、可能的后果和建议的验证方式。不自行决定是否允许发布，不使用统一的“全部通过才发布”规则。
5. **保持简洁。** 默认只报告和当前工作流相关的重点；只有用户希望完整审查时，才展开更多条目。

## 典型关注点

- **工具调用**：超时、断连、429/5xx、参数错误；区分可重试错误与永久错误。
- **恢复语义**：State/Checkpoint 的保存位置、进程重启、并行分支、人工中断后恢复。
- **外部副作用**：写成功但响应丢失、Checkpoint 尚未保存、重复执行与幂等。
- **Agent/RAG 结果**：模型输出格式异常、错误被伪装为空结果、证据引用混乱、循环不终止。
- **发布与安全**：仅对部署为服务或涉及敏感数据的工作流考虑鉴权、隔离、版本兼容与回滚。

可以在 [场景覆盖与可选验证方法](references/fault-injection-matrix.md) 中查找具体示例。它是场景库，不是必须执行的测试清单。

## 给用户的呈现方式

通常用简短的自然语言指出“值得注意什么、为什么相关、从代码看到了什么、如需进一步确认可以怎样测”，不强制输出分数、PASS/FAIL、门禁结论或长报告。

用户明确要求审查记录时，可参考 [可选检查记录模板](references/review-note-template.md)；没有这个要求就不用生成。

## 安全边界

严禁在未经确认的生产或共享环境中注入故障。即便在测试环境，停止进程、修改持久化数据、模拟业务写操作之前也应确认目标与清理方式。若无法安全演练，提供验证思路即可。
