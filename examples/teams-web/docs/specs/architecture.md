# 服务端团队展示

- 一个 loopback Bun 服务持有四个普通 Agent，分别组合独立 Chat 会话、生成、专家提示词、事件发布与同一个 Teams；任意成员可作为任务入口。HTTP、文件与进程 API 留在 Host，可使用 Bun 支持的 Node API。
- 模型连接由宿主通过 MODEL_API_KEY、MODEL_BASE_URL 和 MODEL_ID 配置；团队示例不绑定具体厂商或平台。
- 每个 Agent 的 EventPublisherPlugin 绑定独立 sourceId 和事件出口。服务端为四个出口提供独立 SSE 路径，中心邮箱另有一个 Teams 消息事件源；前端不直接持有 Agent 或消费 JS 生成器。
- Teams 维护唯一信箱事实，在 send/receive 的投递、领取位置发布通知；服务端只记录其展示投影，不创建第二份调度邮箱。领取不表示任务完成。
- 中心邮箱按四名收件人分块，与成员对话顺序一致。每封信显示发件人、内容与领取状态；每块独立滚动，任务重置和历史补发保持相同归类。
- UI 订阅四个成员出口与中心邮箱，只渲染事件。页面关闭不取消服务端运行；客户端断线可使用 SSE 序号补发缓存内的展示事件。
- 页面通过独立 POST 入口向任意成员调用原 `run({ prompt })`。同一服务端团队长期存在，运行中仍可继续提交；RunSteeringPlugin 在成员内部接纳、停止和合批。没有固定 Leader、Top 或全局团队完成条件。
- 演示任务采用给定模拟资料与成本卡，要求研究、方案、核验、成稿的消息交接。模型实际通过 ModelPlugin 发起请求，不能以脚本预设模型输出当作真实协作验收。
- 外部任务只描述目标、约束和产出，不点名安排成员或指定最终回答者。团队通信说明由 Teams 注入，各成员职责由自己的提示词插件提供，内部协作不能依赖调用者写出分工。
- 页面不推断团队完成，不通过角色名、消息正文或正则生成最终报告。每个外部输入只展示其接纳及对应成员 Run 的结果；成员后台协作继续通过 Session、Events 与 Teams 邮箱观察。
- 每个成员的单轮步数预算属于自己的 Host 插件；服务关闭时取消模型请求。页面不提供伪装成团队生命周期的全局停止状态，也不向 Core 注入 runId、messages 或事件回调。
- 连续输入保留到达顺序。首次模型请求前的输入直接合入当前批次；运行中的输入组成下一批，页面逐条显示 user 消息；一批共享物理执行的 value/主错误，各次调用保留独立 Outcome。
- HTTP 限制在本机 loopback，提交入口使用 JSON 与同源核验。Key 只从服务端环境读取；错误返回、展示记录和客户端配置不包含 Key 或原始堆栈。
- 默认不把任务内容或成员事件写盘。只有明确开启展示记录时保存给定非敏感演示数据；记录不是普通用户消息的默认日志策略。
- 前端不执行模型文本或工具内容，使用 textContent 渲染；四个对话框与中心邮箱在窄屏正常换行，连接/失败/空状态有明确文案。
